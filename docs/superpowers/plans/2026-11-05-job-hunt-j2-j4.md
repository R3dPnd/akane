# Job Hunt J2 + J4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Akane reads the morning report aloud once a day and shows it in the chat, acts on "dismiss 2" / "I applied to 1" / "Acme rejected me" / "what was number 3?", runs the hunt herself nightly (on wake if asleep), and runs one on demand ("find me jobs") with an announcement when it finishes.

**Architecture:** A new `announce` path in the runtime (pnd-mcp): `POST /api/v1/announce`. It publishes an `announce` event that the orchestrator speaks when idle, and posts the text into a named chat stream. A delivery service watches for the first moment Akane is ready or spoken to each day and delivers the latest undelivered report once. A `job_search_server` MCP server gives the router the follow-up tools. Akane's launcher adds `akane schedule`, a launchd `StartCalendarInterval` job; launchd runs a missed time on wake, which is the user's choice.

**Tech Stack:** Python 3.12, FastAPI, FastMCP, requests, launchd (`plistlib`, `launchctl`), pytest.

**Spec:** `docs/superpowers/specs/2026-11-04-akane-job-hunt-design.md` (§7.4–§7.6, §7.8, §8 rows J2 and J4). J0–J1 is done; see `docs/superpowers/plans/2026-11-05-job-hunt-j0-j1.md`.

## Global Constraints

- Branches:
  - akane: `job-hunt-j2-j4` from `job-hunt-j0-j1`.
  - pnd-mcp: continue `persona-agnostic`, bumping akane's runtime after each pnd-mcp task.
  - pnd-job-search: untouched in this plan.
  - Push nothing.
- **User decision:** if the Mac is asleep at `job_hunt.run_at`, the hunt runs when it wakes (launchd's default for `StartCalendarInterval`). No `pmset` wake schedule.
- **Spoken once per day.** The report is spoken at most once per calendar day, across restarts (front-matter `delivered_at`). Akane never speaks on her own overnight: delivery happens only when Akane becomes ready (API or voice start) or at the user's first wake word or typed message.
- In silent `akane dev` (no voice pipeline) the report is posted to the chat and still counts as delivered.
- **Spoken text:** about 3 sentences, never URLs. Built deterministically from the leads, with no LLM call.
- The full report goes into the work stream titled **"Morning report"**: one stream, reused, under the first enabled focus area.
- Lead numbers refer to the latest report (spec §7.5). Tools take `n: int`.
- **Always-on tool count ≤ 22**, pinned by an akane config test.
- **Act, don't offer** (spec §7.8). Add this prompt line verbatim to akane's `ollama.system_prompt`: "When the user asks to find jobs, read the morning report, or dismiss, apply to or update a lead, call the tool immediately. Never ask "would you like me to…?" for these."
- Tests never call the real claude CLI, JSearch, or a real launchctl.

## Review Focus

1. **Akane started twice on the same morning** (or restarted after delivery): she must not read the report again. Pinned in Task 2.
2. **A report written while Akane is already running overnight:** nothing is spoken at 4am. Delivery waits for the user's first wake word or typed message. Pinned in Task 2.
3. **"dismiss 9" when the latest report has 8 leads:** a clear "there's no number 9 in today's report" answer, with no exception and no wrong lead. Pinned in Task 3.
4. **The nightly hunt and an on-demand hunt overlap:** the second one reports "already running" and exits 0, so `leads.json` isn't raced. Pinned in Task 4.
5. **An on-demand hunt finishes while Akane is stopped:** its announcement is delivered once at the next start, not lost and not repeated. Pinned in Tasks 2 and 4.

### Task 2: Morning report delivery

**Repo:** pnd-mcp

**Files:**
- Create: `integrations/job_search/delivery.py`, `app/services/morning_report_service.py`
- Modify: `app/main.py` (startup wiring), `integrations/job_search/report.py` (`mark_delivered`)
- Test: `tests/integrations/test_job_search_delivery.py`, `tests/app/test_morning_report_service.py`

**Interfaces:**
- Consumes: Task 1 (`announce` event, `post_assistant_message`); `LeadStore.for_date`/`set_status`; `report.delivered_at`.
- Produces (`delivery.py`):
  - `def spoken_summary(leads: list[Lead], notes: list[str]) -> str`. With leads: "Morning. N new lead(s) overnight. The best three: <org>'s <short title>[ at <pay>]; …. They're in the chat." Titles are cut at the first " - "/"(" and to 60 characters. With none: "Morning. No new leads overnight." With notes: one extra sentence, "One problem: <first note, first sentence>." No URLs, ever.
  - `def report_notes(report_text: str) -> list[str]`: the `> ` lines.
  - `def chat_text(report_text: str) -> str`: the report without its front matter.
  - `def mark_delivered(report_path: Path, when: str) -> None` (in `report.py`): rewrites the front matter's `delivered_at:` line.
  - `def pending_path(data_dir: Path) -> Path`: `<data_dir>/applications/pending_announcements.json`, a list of `{"text", "chat"}`.
  - `@dataclass class Delivery`: `spoken: list[str]`, `chat: list[str]`.
  - `def due(data_dir: Path, today: str, now: str) -> Delivery`. It gathers today's report if its `delivered_at` is empty, plus every pending announcement. It marks them delivered, clears pending, and sets today's leads `new` → `shown`. If nothing is due, it returns an empty `Delivery`.
- Produces (`morning_report_service.py`):
  - `def deliver_now(reason: str) -> bool`. Under a module lock, it calls `due(...)`. For each spoken item it emits `announce`; for each chat item it calls `post_assistant_message("Morning report", text)`. Returns whether anything was delivered.
  - `def install(voice_pipeline: bool) -> None`. It subscribes a bus listener that calls `deliver_now` on `session.start`, on `chat.turn`, and on `state.changed` with `running: true` (the orchestrator is ready, so speech has a listener). When `voice_pipeline` is False, it also calls `deliver_now("startup")` once.
- `app/main.py` startup calls `morning_report_service.install(voice_pipeline=not no_voice)` after the orchestrator thread is started.

### Task 3: Follow-up tools (`job_search_server`)

**Repo:** pnd-mcp

**Files:**

**Interfaces:**
- Consumes: `LeadStore`, `JobSearchApp`, `delivery.chat_text`.
- Produces (client):
  - `create_application(company, role, job_url, date_applied: str | None, source: str) -> dict` (`POST /applications`)
  - `list_applications() -> list[dict]` (unwraps `applications`)
  - `stages(app_id) -> list[dict]` (unwraps `stages`)
  - `advance(app_id, stage_id) -> dict` (`POST /applications/{id}/advance` with `{"stage_id"}`)
  - `update_status(app_id, status) -> dict` (`PATCH /applications/{id}` with `{"status"}`)
- Produces (MCP tools, FastMCP like the other servers; base URL from env `PND_JOB_SEARCH_URL`, default `http://localhost:8080/api/v1`; store at `data_dir()/applications/leads.json`):
  - `get_morning_report() -> str`: the latest report's chat text, or "No report yet — say 'find me jobs' to run a hunt."
  - `get_lead(n: int) -> str`
  - `dismiss_lead(n: int) -> str`: app leads also call `app.dismiss`.
  - `mark_applied(n: int) -> str`:
    - app leads: `track(id, applied=True)`;
    - gig leads: `create_application(org, title, url, today, "akane:gig")`;
    - then advance the application to the stage named "Applied" (case-insensitive) when it isn't already there;
    - the lead's status becomes `applied`.
  - `update_application(company: str, status: str) -> str`: finds the application whose company contains `company` (case-insensitive; with several matches, picks the most recently updated and says so). Mapping (spec §7.6):
    - applied → stage "Applied";
    - interviewing → the next of Phone Screen → Technical Interview → Final Round after the current stage;
    - offer → stage "Offer" and status `offer`;
    - rejected → stage "Rejected" and status `rejected`;
    - closed → status `archived`.
    - An unknown status gives a message listing the five.
  - `start_hunt() -> str`: Task 4.
  - Every tool returns a short sentence the router can speak, and catches `JobSearchUnavailable` into "I couldn't reach your job search app".
  - A number not in the latest report gives "There's no number N in the latest report (it has M)." (Review Focus 3)

### Task 4: On-demand and overlapping hunts

**Repo:** pnd-mcp

**Files:**
- Modify: `integrations/job_search/__main__.py` (`--announce`, lock), `integrations/servers/job_search_server.py` (`start_hunt`)
- Test: `tests/integrations/test_job_search_hunt.py`, `tests/integrations/test_job_search_server.py`

**Interfaces:**
- Produces:
  - `hunt` takes an exclusive non-blocking `fcntl.flock` on `<data_dir>/applications/hunt.lock`. If another hunt holds it, it prints "A hunt is already running." and exits 0 (Review Focus 4).
  - `hunt --announce`: after the run, it builds `spoken_summary(added, notes)`, reworded to start "Your job hunt is done." instead of "Morning.", plus the report's chat text. It sends them with `POST {api_base}/announce` (`chat_title: "Morning report"`), where `api_base` is `http://localhost:<persona.api_port>/api/v1`. On success it marks the added leads `shown`. If the POST fails, it appends `{"text", "chat"}` to `pending_announcements.json`.
  - The nightly run (no `--announce`) doesn't announce; morning delivery (Task 2) handles it.
  - `start_hunt()` starts a detached `sys.executable -m integrations.job_search hunt --announce` (`start_new_session=True`, `cwd=` the runtime dir, the environment passed through). It returns "On it — I'll tell you when the hunt is done." If the lock is held, it returns "A hunt is already running."
